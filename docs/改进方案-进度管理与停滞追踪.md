# OpenGantt 改进方案：进度管理 · 停滞追踪 · 员工投入度分析

> 基于 2026-10-16 系统现状与真实数据盘点制定，所有方案均标注数据来源与改动面，  
> 按 P0/P1/P2 分期实施，可直接按期开工。

## 一、现状盘点：我们手里已经有什么

| 已有能力          | 数据基础                                        | 对目标场景的价值                   |
| ------------- | ------------------------------------------- | -------------------------- |
| 任务进度每日快照      | `progress_logs`（每天每任务一条：进度 + 说明 + 记录人 + 时间） | **停滞检测与趋势分析的数据金矿**，历史已自动积累 |
| 任务负责人关联       | `tasks.assignee_id` → 账号                    | 可精确到"人"统计投入度               |
| 每日 17:30 自动归档 | `daily_reports`（每账号每日一份日志）                  | 可挂载停滞预警，形成日报机制             |
| 关键决策记录        | `daily_notes`                               | 决策留痕，复盘有据                  |
| 角色与部门体系       | admin / supervisor / employee + 6 部门        | 看板可按角色分权展示                 |
| 文档归档          | 项目进度文档上传下载                                  | 佐证材料                       |

**当前数据实测信号**（演示库）：

- 逾期未完成任务 **2 项**（#1 需求分析 70%、#2 架构选型 90%，计划结束日均已过）
- 员工进度记录活跃度差异明显：张三 4 条、李四 2 条、赵六/王五 各 1 条
- 系统尚无"停滞""逾期""未投入"的**显式计算与展示**——数据在、结论不在，这正是本方案要补的

**关键缺口**：任务只有进度百分比、没有显式状态（阻塞/暂停只能靠说明文字猜）；没有看板；  
没有按人的活跃度视图；任务查询只有"按项目浏览"一种方式。

## 二、任务状态跟踪机制（P0，地基）

### 2.1 任务状态字段

为任务增加显式状态，替代目前"进度 ≥100% 即完成"的隐式判断：

```
not_started 未开始 → in_progress 进行中 → blocked 阻塞 → paused 暂停 → done 已完成
                                        ↘ cancelled 已取消
```

- **进度与状态解耦**：进度 80% 也可以"阻塞"（当前真实场景：#2 架构选型 90% 但卡在签字确认）
- **blocked 强制填阻塞原因**（结构化字段，替代现在的关键词识别，第三节的"阻塞/需协调"直接取数）
- 甘特图任务条按状态着色：红=阻塞、灰=暂停、蓝=进行、绿=完成、浅灰=未开始——**一眼看出哪条卡住了**
- 改动面：`tasks.status` 列（迁移脚本自动加列）+ 表格状态下拉 + 甘特条配色 + API 校验

### 2.2 停滞判定规则（自动计算，每日随 17:30 归档刷新）

| 规则        | 判定                                   | 数据来源                   |
| --------- | ------------------------------------ | ---------------------- |
| **进度停滞**  | 连续 N 个工作日 progress 无变化 且状态=进行中       | `progress_logs` 相邻快照对比 |
| **无反馈停滞** | 连续 N 天进度说明为空                         | `progress_logs.note`   |
| **逾期未完成** | `end_date < 今天` 且状态 ≠ done/已取消       | `tasks` 表              |
| **计划偏差**  | 期望进度 =（今天-开始）/（结束-开始），实际 − 期望 ≤ −20% | `tasks` 日期推算           |

> ⚠️ 注意：因为系统每天自动保存快照，**"停滞"必须定义为"进度值连续无变化"**，  
> 而不是"没有快照记录"——否则 17:30 自动保存会让所有任务看起来"每天都很活跃"。

**风险分级输出**：🟢 正常 / 🟡 关注（命中 1 条规则）/ 🔴 停滞（命中 2 条或逾期超 3 天）。  
每次变更记录 `task_status_logs`（谁、何时、从什么状态改到什么状态、原因），可审计、可追溯。

### 2.3 展示位置

- 部门页任务表格：新增"状态"列与"风险"徽标（🔴🟡🟢）
- 甘特图：条形按状态着色 + 停滞任务条加斜纹
- 每日工作日志：第三节"阻塞/需协调"改为从结构化状态取数（不再关键词猜）

## 三、数据统计与可视化（P1，驾驶舱页面）

新增 `/dashboard` 页面（主管与管理员可见，员工版只看自己），推荐 **ECharts**（Apache-2.0，免费商用，中文文档完善）：

| 图表        | 内容                               | 数据来源                               |
| --------- | -------------------------------- | ---------------------------------- |
| 部门进度总览    | 各部门项目平均进度横向条形图，红黄绿分段             | projects + tasks 聚合                |
| 逾期 & 停滞看板 | 两张清单卡片（🔴逾期、🟡停滞），点击直达任务         | 第二节规则计算结果                          |
| 进度趋势折线    | 选定项目/人员，按天的进度曲线（可叠加期望进度虚线）       | `progress_logs` 历史序列——**无需新增任何采集** |
| 员工投入度排行   | 近 7/30 天：进度更新次数、说明填写率、名下任务平均停滞天数 | `progress_logs` 按人聚合               |
| 活跃热力图     | 日历热力图：每人每天是否有进度更新（GitHub 风格）     | `progress_logs` 按人按天               |
| 任务分布环图    | 全部任务按状态/按部门分布                    | tasks 聚合                           |

员工视角"我的看板"：我的任务列表、我的停滞项提醒、我的说明填写率——让员工自查先于被查。

## 四、识别未投入工作的员工（P1，口径先行）

**原则：系统给数据指标，不贴人为标签**——输出"投入度参考报告"，由主管结合实际判断，  
避免工具误伤（请假、跨项目支援等情况）。

### 4.1 客观指标（全部可从现有数据计算）

| 指标    | 口径建议                                      | 数据来源                      |
| ----- | ----------------------------------------- | ------------------------- |
| 更新次数  | 近 7 天名下任务进度更新 = 0 → 🚩                    | `progress_logs` 按 user 统计 |
| 停滞天数  | 名下任务平均"距上次进度变化"天数 > 5 → 🚩                | 快照对比                      |
| 说明填写率 | 近 14 天有快照的天数中写了说明的占比 < 30% → 🚩           | `progress_logs.note`      |
| 登录活跃  | `users.last_login_at`（新增字段）超过 7 天未登录 → 🚩 | 登录时更新                     |

### 4.2 输出形式

- 管理后台新增"投入度分析"页签：按部门分组的员工指标表格，🚩 员工置顶
- 每日 17:30 归档时，为每位**主管**额外生成"停滞与投入度日报"（挂在现有日志归档机制上，零新增调度）
- 支持导出 .md / .xlsx（复用管理员导出通道）

## 五、查询效率与易用性（P1~P2）

### 5.1 后端查询能力

- 任务列表接口增加：**分页 + 多条件筛选**（项目/部门/负责人/状态/逾期/停滞/关键字模糊）+ 排序
- 数据库索引：`tasks(project_id)`、`tasks(assignee_id)`、`progress_logs(user_id)`、  
  `progress_logs(log_date)`（task_id+log_date 唯一索引已存在）
- 新增聚合端点：`/api/stats/overview`（看板一次取全量汇总，避免前端多次往返）

### 5.2 前端易用性

- **全局搜索**（顶栏 Ctrl+K）：任务名 / 负责人 / 项目名一键直达
- **快捷过滤页签**（部门页表格上方）：`我的任务` `本周到期` `已逾期` `🟡停滞`——高频场景一键切换
- 表格列显隐 + 偏好记忆（localStorage）
- 批量操作：多选任务 → 批量改负责人/状态/日期（复用现有 bulk 原子更新接口）
- **Excel 导入导出**：任务排期用 Excel 批量流转（openpyxl，MIT 协议）

### 5.3 通知渠道（P2，可选）

- 17:30 归档完成后，可选推送：邮件（smtplib 标准库零依赖）或企业微信群机器人 webhook（免费）
- 推送内容：停滞/逾期任务清单 + 员工投入度摘要（主管收全量、员工收自己的）

## 七、需要确认的口径（开工前请拍板）

1. **停滞阈值**：连续几个工作日进度无变化算停滞？（建议 3 个工作日）
2. **"未投入"窗口**：近 7 天 0 次更新 + 名下有任务，是否合适？（建议 7 天）
3. **状态枚举**：是否需要"已取消"？是否允许"已完成"回退？
4. **通知渠道**：暂不推送（页面查看）还是接邮件/企业微信？
5. **数据可见范围**：投入度指标普通员工是否互相可见？（建议仅主管与管理员可见，员工只看自己）

确认后即可按 P0 → P1 → P2 顺序开工。
